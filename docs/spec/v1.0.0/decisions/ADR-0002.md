# ADR-0002: Proposed identity and MFA model for M1

Status: **Proposed - pending provider, TLS and deployment approval**
Date: 4 November 2026

## Context

The application owns backup/restore metadata for several independent projects. Trusting client-supplied user identifiers, shared passwords, or role claims would allow horizontal privilege escalation. The daemon initially runs only over loopback HTTP and cannot safely receive bearer credentials until TLS transport is configured.

## Proposed direction

- Delegate actual user sign-in and MFA to a standards-based identity provider (provider choice remains open). Use an OAuth 2.0/OIDC authorisation-code flow with PKCE for interactive clients in the next slice.
- For API authentication, accept only signed RFC 9068 JWT **access tokens** intended specifically for the backup-manager API. Never accept an OIDC ID token as an API bearer token. Enforce exact issuer, audience, signing key ID, client ID and an agreed signed MFA assurance (`acr`). Reject tokens with missing MFA assurance.
- Allow only RS256 with an explicitly pinned RSA public key during the initial implementation. Key rotation and provider discovery require a later reviewed design.
- Require the issuing identity to match an **existing active** local account via an issuer-and-subject key. Do not automatically create users or administrators based on token claims. Only offline operations can initially grant instance-administrator access.
- Keep project membership and roles in the SQLite catalogue. All API authorization is server-side; re-evaluate instance privileges on each relevant write. Treat unauthorised and nonexistent project identifiers consistently.
- Keep access tokens short lived (at most 15 minutes) and store SHA-256 fingerprints, not tokens, for local token revocation. Local revocation does not log the user out of their identity provider.
- No cookie-based browser login or CSRF trust is enabled yet; browser-origin writes remain blocked. Enable browser sessions only with reviewed secure-cookies/CSRF controls and protected TLS/private access.
- Do not configure the production daemon with real bearer authentication while it serves plaintext HTTP. It must remain deny-all until secure TLS transport and provider configuration are implemented.

## Consequences and outstanding decisions

1. Approve OIDC provider, verified `acr` policy and resource-specific `aud`/`client_id` profile.
2. Implement a trusted TLS endpoint and key rotation without exposing public management ports.
3. Implement interactive PKCE login/logout, session expiry, CSRF/origin controls and revocation.
4. Define privileged offline account provisioning and account recovery, including secure service-account access to the catalogue.
5. Test Mac launchd, Keychain and multiple-user sessions on target hardware.

This ADR is not final approval to turn on the management API. M1-04A delivers the token verifier and server-side RBAC building blocks, but **not** usable sign-in.
